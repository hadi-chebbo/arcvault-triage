# How I used AI on this project

I built this with Claude Code as a pair programmer. This log records where I disagreed with the AI or where it got something wrong, and what I did about it.

## Outage detection: I rejected the AI's keyword rule

Claude's first design detected outages in two ways: the classification model chose an Incident/Outage Category, and a keyword rule acted as a backup that escalated any Request containing phrases like "outage", "down for" or "multiple users". I had accepted this during design, but when I read the code I pushed back. A keyword list doesn't understand meaning: it misses "nobody on our team can get in", and it would flag "we had an outage last year, all fine now". Claude argued that a backup can only add Escalations, never remove them, so its mistakes are cheap (a human looks at something unnecessary) while a missed outage is expensive. I then raised the opposite risk: the AI could classify correctly and the backup be the one that gets it wrong. If that happens often, people learn to ignore the Escalation queue and the backup protects nothing. We agreed on a better design. The keyword rule was removed and replaced by an Outage Signal, a second, independent AI judgement made during the enrichment step. A Request escalates if either AI call sees an outage, so both checks come from understanding the text, and disagreement between them is itself a useful sign that a human should look. I also added false-alarm test cases (messages that sound like outages but aren't) so the evaluation measures how often the backup is wrong instead of assuming it.

## Smaller fixes

- Claude recommended Llama 3.3 70B on Groq from its own knowledge, but when we checked Groq's live model list, the model had been retired. We tested the two remaining general-purpose models on a sample and switched to `openai/gpt-oss-120b`. Lesson: check what a provider actually offers instead of trusting an AI's memory.

- The test command Claude first wrote (`node --test test/`) failed on Node 26, which no longer accepts a folder name. It was changed to a file pattern.
- The code review found that the first version of the routing rules let malformed AI answers through (a missing confidence score, a null response, a category like "toString"). They were fixed so that anything malformed escalates to a human.
- The subagent that built ticket 02 reported that importing and publishing the workflow worked. It did, but only the first time. Code review and a live test showed that every later import reused n8n's previous version id, so n8n kept serving the old code. I gave each import a fresh version id and verified it live. Lesson: "it worked once" isn't verified; test the path you will actually use repeatedly.
- `crypto.randomUUID()`, the usual way to make an ID in JavaScript, doesn't exist inside n8n's Code node sandbox. The first Request without an id failed with "Error in workflow". It now uses a timestamp plus random letters.
- The model's Confidence for sample #4 (Okta SSO) changed between identical runs (0.78, 0.96, 0.75), even at temperature 0. A single self-reported Confidence isn't stable enough to trust alone; this shaped the evaluation in ticket 04.
- The enrichment prompt asked for "error codes" but the model still dropped "403" from sample #1 and "Okta" from #4. Calling Groq directly with the same prompt showed the prompt needed a concrete example for each kind of Identifier, not just a list of names.
- n8n briefly kept serving the previous workflow version after each import, so a test right after an import silently used the old prompt. The first fix (wait until the webhook answers) didn't work, because the old version answers too. The import now stamps a unique build id into the workflow and waits until n8n returns that exact id.
- I misread a result. Sample #4 landed in Escalation, and I told my reviewer-self it was low Confidence. The code review showed it was a Groq rate-limit error (HTTP 429) that the pipeline correctly turned into an `ai_failure` escalation. Lesson: read the record's error field before drawing conclusions from where it landed.
- To save tokens, I tried the model's "low" reasoning effort for enrichment. It was faster and cheaper on sample #1, so it looked fine, but a full run showed it dropped Identifiers on samples #2 and #5. I reverted it and spaced the Requests out instead. Lesson: test a change on the whole sample set, not one example.

## Evaluation (ticket 04)

I ran every sample 3 times through the live workflow (11 samples, 33 Requests) and compared each Triage Record with `samples/expectations.json`. The edge cases all passed: the over-$500 Overcharge escalated, both false alarms ("we had an outage last year, fine since" and "one user can't see the dashboard") were not escalated, the vague "it doesn't work" got Confidence 0.60 and escalated, and the French outage escalated. What the AI got wrong, or where its answers didn't match my expectations:

- **Sample #4 was more confident than the spec expected.** The spec said "is there a way to set up SSO with Okta?" is ambiguous and should escalate with low Confidence. In all 3 runs the model called it a Technical Question at 0.75–0.80, so it went to Customer Success. I noticed it as the only failing row in the evaluation table. I could have tuned the prompt until this one sample dropped below 0.70, but that is overfitting to a test, and it risks escalating every ordinary how-to question. Customer Success is a reasonable place for it: they can answer, or log a Feature Request if ArcVault doesn't support Okta. I changed the expectation instead, and recorded why in the spec.
- **Identical input, different Category.** The mixed bug-and-billing message ("export throws error 500 … charged twice") was a Bug Report in 2 runs and a Billing Issue in 1, at temperature 0. Both are acceptable, but it confirms the model isn't deterministic on borderline Requests. This is why the evaluation runs each sample several times and reports the spread, and why self-consistency is in Phase 2.
- **The subagent's evaluation script trusted error replies.** A Sonnet subagent built the evaluation command. On review I found it only treated a reply as a failed call when the body wasn't JSON. An n8n error reply is JSON, so it would have been checked as a Triage Record and shown as 20 confusing "missing field" failures. It now checks the HTTP status and the reply's shape first, reports one clear "request failed" line, and counts failed calls apart from misclassifications, like AI errors. The same review found that the shared webhook helper would have let `npm run send` save an n8n error reply into the records file; it now stops instead.
- **Claude overwrote real results with a test run.** While checking the fix offline, Claude ran the evaluation against a dead URL. That run wrote its single failed row over the edge-case results file from the real baseline run. The file wasn't committed yet, so the edge set was re-run. Lesson: a quick test run should write somewhere else, or be run before the real one.
